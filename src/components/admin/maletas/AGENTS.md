# Maletas e remessas
- Remessa (table remessas, unique numero, one praça) is the parent of maletas: kit_cycles.remessa_id, opened only via remessa_abrir_maleta (consultant must belong to the remessa's praça, one maleta per consultant per remessa); print docs read número/praça/acerto from the remessa. Why: remessa is the master control entity.
- Referral (indicação) commissions are computed only by a DB trigger when a kit cycle closes, stored once per cycle in referral_commissions with an item snapshot; why: transparent, idempotent, never recalculated retroactively when tiers change.
- Maleta acceptance under signature mode goes only through kit_assinatura_finalizar (Clicksign signed file stored first; trigger on kit_acceptances blocks direct accept unless mode is desligado). Why: release requires the consultant's own signed term.
- Montagem-by-scanner goals come from montagem_metas_ciclo (0113): read-only, staff only, categories mapped by legado_categoria_tipo (Master edits via legado_categoria_tipo_definir, audited); on error the scanner falls back to remessa_parametros. No text input in the scanner overlay (focus returns to the barcode field every 400 ms). Why: suggestion never touches stock or the kit.
- Consultant maletas (0120): consultora_maletas/maletas_visibilidade are read-only; a Lardan maleta shows in the consultant app only in expedida/transito/recebida/operacao/acerto and when her active login is on the SAME party (duplicates hide it); SmallData open maletas exist only in legado_*. Why: explain "maleta não aparece".
- Lost maletas (0130): one row per lost maleta in maletas_perdidas (SmallData tipo perdida/status 11, or Lardan via kit_maleta_perdida); no NF; fiado = retail of pieces not returned, title sistema_origem maleta_perdida on FIADO-PERDA (outside DRE) + cob_fiado_linhas lote maleta_perdida, idempotent; skip-acerto via kit_pular_acerto / legado_maleta_pular_acerto (next acerto of the same praça); remessa maletas may go to the representante without consultora (remessa_abrir_maleta_representante) and he assigns a consultora or own candidata via rep_maleta_repassar.
- Consignment order sheet + price (0157): the A4 order is built by src/lib/pedido-consignacao.ts from kit_pedido_dados (items grouped by type via pedido_grupo_peca, prices = unit_reference_cents recorded in the kit composition, commission tiers from consultora_comissao_faixas, fixed texts from pedido_config — Master only via pedido_config_salvar); 'Postar a maleta até' only when remessas.tipo_envio = 'correio' (acerto − prazo_correio_dias). Consultant app, showcase, client orders and lost-maleta value use kit_preco(cycle, variant) (recorded price), never the catalog price of the day. New price rule preco_regra_lardan (always up: ,90 below R$100; 4,90/9,90 from R$100) is applied only via preco_reajuste_aplicar (Master, typed confirmation, after the preco_reajuste_previa report is approved), logged in preco_reajustes, undo by lote; shipped kits keep their recorded price, kits still in montagem move to the new price. Why: kits settle at the price on their label.
- Settlement in the app / pre-baixa (0158): kit_pre_baixas + kit_pre_baixa_itens per cycle; the consultant marks sold pieces (pre_baixa_vender; paid/concluded app orders are pre-marked and can't be lowered), closes with pre_baixa_fechar (sold at recorded price, commission tier on the consultant's whole remessa, payable = sold − commission → receivable title sistema_origem pre_baixa via the cobrança config actor; Pix via preBaixaFecharPix + pre_baixa_asaas_preparar). Staff confer by scanning (pre_baixa_conferir preview/apply): expected return = sent − declared sold; missing = sold at recorded price, declared-sold that came back = refund; returned pieces go back through kit_retorno/kit_retorno_confirmar, qty_sold is set, cycle closes; any difference → 'pendencia' (receivable for the difference or credit noted) resolved via pre_baixa_pendencia_resolver. New kit requires the previous kit's pre-baixa closed only when pedido_config.exigir_pre_baixa is on (Master; one-time release pre_baixa_liberar_kit). Why: exact settlement before the kit is back, divergence becomes a traceable pending item.

- Consultant app (0159): a client order paid to Lardan (Asaas allocation on sales_orders.pay_installment_id) turns pago/concluido by trigger pedido_pagamento_sincronizar (reversal → estornado); "cliente pagou em dinheiro" only via consultora_pedido_pago_dinheiro (pay_method 'dinheiro', money stays with the consultant, never on an order that already has a Lardan charge). The acerto deducts what clients already paid to Lardan (pre_baixa_recebido_lardan → kit_pre_baixas.recebido_lardan_cents; payable = sold − commission − received; ≤ 0 creates no title). consultora_meu_financeiro / consultant_home are owner-scoped (my_party_id); 2ª via only for her own receivable via consultora_debito_cobranca + server-only consultora_debito_asaas_preparar. Referral: "Quem te indicou?" text is kept in leads.indicado_por_texto and links only on an exact referral_code; the referred lead/profile inherits the sponsor's representative/praça only when empty; madrinha corrected only via consultora_madrinha_definir (registry.manage, audited). Leader path: criteria in lider_config (Master), leader status in lideres (request by the consultant, decision only by Master via lider_decidir); Minha equipe only for approved leaders and shows first name + initial; leader commission is stored but off. Liga levels in liga_niveis (Master via liga_niveis_salvar) count settled cycles in 12 months (Lardan pre-baixa + SmallData legado_maletas). Why: the app must show real money and real pending items without exposing other people's data.
- Review fixes (0163): a client payment (Pix/card trigger or "pagou em dinheiro") marks the order pago but never concludes it (conclusion still requires the sale record, as in order_set_status); aguardando_pagamento → em_atendimento. Conference recomputes what clients paid to Lardan (pre_baixa_recebido_lardan) so a payment after closing becomes a credit, never a double charge; a pre-baixa with payable ≤ 0 counts as paid. Cash received by a representative on an installment with an open Asaas charge returns aviso_asaas and opens a cob_tarefas to cancel the link. Why: no double charge, no orders stuck in "concluído" without the sale record.
